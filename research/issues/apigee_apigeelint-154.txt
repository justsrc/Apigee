--- BODY ---
Rule PO008 is requesting developers to use a file name for their policies that matches the policy's display name. This is inconsistent to Apigee's default behavior when exporting code.

When you develop a new proxy via the Apigee Management UI and then download the proxy revision, the file names of the policies match the technical names of the policies, not the display names.

I have verified behavior by modifying downloaded code as per the rule PO008 requirement, then uploading to Apigee and downloaded again. The upload was working (so no issue if you do follow the rule), but downloaded result again contains the technical names of the policies as file names.
So whenever you are up- and downloading code via the Management UI, you would end up in the need to modify the file names over and over again.

As a consequence I would rather suggest to drop rule PO008 from the standard set of rules (for backward compatibility) and to implement a new rule that checks for matching file name with the technical name of a policy.

### comment by karsten-wagner (association=NONE) at 2020-09-14T16:53:48Z
Thanks for picking this up.

Since something may have been lost in translation, the following reads as:
FileName = the name of the file that stores XML code of a single policy (on your local disk)
DisplayName = the XML tag inside the policy that is called "<DisplayName>"
PolicyName = the "name" attribute of a the XML tag that defines a policy (e.g. "<AssignMessage name='AM-DemoVariables'>")

At the moment I feel forced to have {FileName == DisplayName == PolicyName}. If this is the case, I wonder why a DisplayName exists at all. From the [Apigee Docs](https://docs.apigee.com/api-platform/fundamentals/best-practices-api-proxy-design-and-development#developmentstandards-namingconventions) I have rather understood that the DisplayName should be "human readable", while the technical names serve the purpose for the machine to identify the policy. Some of the common naming conventions recommend to have a prefix, which explains the type of the policy (e.g. "AM" = "AssignMessage"). This helps in other places of the code (e.g. proxy/target definitions) to better understand what type of action is performed.
Omitting the DisplayName for very technical oriented teams may be feasible. It ends up in the same behavior as setting {DisplayName == PolicyName}. So far so good...

In my team we feel the "human readable" part of the name should be somehow similar as the technical name, but would usually also contain spaces (no Pascal Case) and not contain the policy prefix (because you see the icon in the UI). So a typical policy could look like this:
```text
<?xml version="1.0" encoding="UTF-8" standalone="yes" ?>
<AssignMessage name="AM-SetOkResponse" continueOnError="false" enabled="true">
    <DisplayName>Set default OK response message</DisplayName>
  <Set>
    <StatusCode>200</StatusCode>
    <ReasonPhrase>OK</ReasonPhrase>
    <Payload contentType="text/plain">Hello World!</Payload>
  </Set>
</AssignMessage>
```

We would then set {FileName == PolicyName}, so explicitly "AM-SetOkResponse.xml". As a consequence the current rule PO008 complains the FileName does not match the DisplayName of "Set default OK response message".  

The Apigee behavior on downloading a proxy bundle ensures {Filename == PolicyName}. Uploading manually created policies where {Filename != PolicyName} is possible. Here I see it more as a hygiene factor to have both the same to ease up navigation in your IDE. Once you download this bundle again, then {Filename == PolicyName} - so Apigee ignores whatever FileName you have provided and upon download the FileName always matches the PolicyName. (i.e. if I set FileName to foo.xml, then upload and finally download above example, then FileName would be "AM-SetOkResponse.xml" in the downloaded ZIP file n my experience.)

Given the default behavior of Apigee to set {FileName == PolicyName}, I do not see the value add of rule PO008 and therefore have suggested to drop it.
At the moment we are doing what @kurtkanaskie has recommended and execute `apigeelint -e PO008 ...`.

I like the approach suggested by @DinoChiesa in having both rules checking one part of the chain. This way teams can decide to use PO006, PO008, or both.

For us it would mean to always execute with `-e PO008`, so I wonder if there could be a config file to select what rules are active (similar to defining your own gitleaks profile)?! The other way could be to to offer the new code of PO008 as custom plugin for teams to activate on their own, but I realize in this discussion there seem to be some friends of using both rules :-)
