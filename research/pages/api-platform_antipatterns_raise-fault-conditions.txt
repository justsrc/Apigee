<p style="text-align: right;"><span style="background-color: var(--tenant-background-3); font-size:12pt"><em>This page
applies to <strong>Apigee</strong> and <strong>Apigee hybrid</strong>.</em></p>
<p style="text-align: right;"><span style="background-color: var(--tenant-background-3); font-size:12pt">
  <em>View <a href="https://docs.apigee.com/api-platform/antipatterns/raise-fault-conditions" target="_blank">
    Apigee Edge</a> documentation.</em></span></p>

<p>
  The <a><a href="/apigee/docs/api-platform/reference/policies/raise-fault-policy">RaiseFault policy</a></a> lets API developers initiate an error flow, set error variables
  in a response body message, and set appropriate response status codes. You can also use the RaiseFault
  policy to set flow variables pertaining to the fault, such as, <code translate="no" dir="ltr">fault.name</code>, <code translate="no" dir="ltr">fault.type</code>,
  and <code translate="no" dir="ltr">fault.category</code>. Because these variables are visible in analytics data and Router access logs
  used for debugging, it's important to identify the fault accurately.
</p>
<p>
You can use the RaiseFault policy to treat specific conditions as errors, even if an actual error has
  not occurred in another policy or in the backend server of the API proxy. For example, if you want
  the proxy to send a custom error message to the client app whenever the backend response
  body contains the string <code translate="no" dir="ltr">unavailable</code>, then you could invoke the RaiseFault policy as
  shown in the code snippet below:
</p>

<div></div><devsite-code><pre class="devsite-click-to-copy" translate="no" dir="ltr" is-upgraded syntax="World of Warcraft TOC" syntax-guessed>&lt;<span class="devsite-syntax-n">!-- /antipatterns/examples/raise-fault-conditions-1.xml  --</span>&gt;
&lt;<span class="devsite-syntax-n">TargetEndpoint name="default"</span>&gt;
<span class="devsite-syntax-n">...</span>
<span class="devsite-syntax-n">  &lt;Response&gt;</span>
<span class="devsite-syntax-n">    &lt;Step&gt;</span>
<span class="devsite-syntax-n">      &lt;Name&gt;RF-Service-Unavailable&lt;/Name&gt;</span>
<span class="devsite-syntax-n">      &lt;Condition&gt;(message.content Like "*unavailable*")&lt;/Condition&gt;</span>
<span class="devsite-syntax-n">   &lt;/Step&gt;</span>
<span class="devsite-syntax-n">  &lt;/Response&gt;</span>
<span class="devsite-syntax-n">...</span></pre></devsite-code>

<p>
The RaiseFault policy's name is visible as the <code translate="no" dir="ltr">fault.name</code> in <a href="/apigee/docs/api-monitoring">
  API Monitoring</a> and as <code translate="no" dir="ltr">x_apigee_fault_policy</code> in the Analytics and Router access logs.
  This helps to diagnose the cause of the error easily.
</p>
<h2 id="antipattern" data-text="Antipattern" tabindex="-1">Antipattern</h2>

<h3 id="using-the-raisefault-policy-within-faultrules-after-another-policy-has-already-thrown-an-error" data-text="Using the RaiseFault policy within FaultRules after another policy has already thrown an error" tabindex="-1">Using the RaiseFault policy within FaultRules after another policy has already thrown an error</h3>

<p>
Consider the example below, where an OAuthV2 policy in the API Proxy flow has failed with an <code translate="no" dir="ltr">InvalidAccessToken</code>
  error.  Upon failure,  Apigee will set the <code translate="no" dir="ltr">fault.name</code> as <code translate="no" dir="ltr">InvalidAccessToken</code>, enter into
  the error flow, and execute any defined FaultRules. In the FaultRule, there is a RaiseFault policy named
  <code translate="no" dir="ltr">RaiseFault</code> that sends a customized error response whenever an <code translate="no" dir="ltr">InvalidAccessToken</code>
  error occurs.  However, the use of RaiseFault policy in a FaultRule means that the <code translate="no" dir="ltr">fault.name</code>
  variable is overwritten and masks the true cause of the failure.
</p>

<div></div><devsite-code><pre class="devsite-click-to-copy" translate="no" dir="ltr" is-upgraded syntax="World of Warcraft TOC" syntax-guessed>&lt;<span class="devsite-syntax-n">!-- /antipatterns/examples/raise-fault-conditions-2.xml  --</span>&gt;
&lt;<span class="devsite-syntax-n">FaultRules</span>&gt;
<span class="devsite-syntax-n">  &lt;FaultRule name="generic_raisefault"&gt;</span>
<span class="devsite-syntax-n">    &lt;Step&gt;</span>
<span class="devsite-syntax-n">        &lt;Name&gt;RaiseFault&lt;/Name&gt;</span>
<span class="devsite-syntax-n">        &lt;Condition&gt;(fault.name equals "invalid_access_token") or (fault.name equals "InvalidAccessToken")&lt;/Condition&gt;</span>
<span class="devsite-syntax-n">    &lt;/Step&gt;</span>
<span class="devsite-syntax-n">  &lt;/FaultRule&gt;</span>
&lt;<span class="devsite-syntax-n">/FaultRules</span>&gt;</pre></devsite-code>

<h3 id="using-raisefault-policy-in-a-faultrule-under-all-conditions" data-text="Using RaiseFault policy in a FaultRule under all conditions" tabindex="-1">Using RaiseFault policy in a FaultRule under all conditions</h3>

<p>
  In the example below, a RaiseFault policy named <code translate="no" dir="ltr">RaiseFault</code> executes if the <code translate="no" dir="ltr">fault.name</code>
  is not <code translate="no" dir="ltr">RaiseFault</code>:
</p>

<div></div><devsite-code><pre class="devsite-click-to-copy" translate="no" dir="ltr" is-upgraded syntax="World of Warcraft TOC" syntax-guessed>&lt;<span class="devsite-syntax-n">!-- /antipatterns/examples/raise-fault-conditions-3.xml  --</span>&gt;
&lt;<span class="devsite-syntax-n">FaultRules</span>&gt;
<span class="devsite-syntax-n">    &lt;FaultRule name="fault_rule"&gt;</span>
<span class="devsite-syntax-n">        ....</span>
<span class="devsite-syntax-n">        &lt;Step&gt;</span>
<span class="devsite-syntax-n">            &lt;Name&gt;RaiseFault&lt;/Name&gt;</span>
<span class="devsite-syntax-n">            &lt;Condition&gt;!(fault.name equals "RaiseFault")&lt;/Condition&gt;</span>
<span class="devsite-syntax-n">        &lt;/Step&gt;</span>
<span class="devsite-syntax-n">    &lt;/FaultRule&gt;</span>
&lt;<span class="devsite-syntax-n">/FaultRules</span>&gt;</pre></devsite-code>

<p>
  As in the first scenario, the key fault variables <code translate="no" dir="ltr">fault.name</code>, <code translate="no" dir="ltr">fault.code</code>,
  and <code translate="no" dir="ltr">fault.policy</code> are overwritten with the RaiseFault policy's name. This behavior makes
  it almost impossible to determine which policy actually caused the failure without accessing a trace
  file showing the failure or reproducing the issue.
</p>

<h3 id="using-raisefault-policy-to-return-a-http-2xx-response-outside-of-the-error-flow." data-text="Using RaiseFault policy to return a HTTP 2xx response outside of the error flow." tabindex="-1">Using RaiseFault policy to return a HTTP 2xx response outside of the error flow.</h3>

<p>
  In the example below, a RaiseFault policy named <code translate="no" dir="ltr">HandleOptionsRequest</code> executes when
  the request verb is <code translate="no" dir="ltr">OPTIONS</code>:
</p>

<div></div><devsite-code><pre class="devsite-click-to-copy" translate="no" dir="ltr" is-upgraded syntax="World of Warcraft TOC" syntax-guessed>&lt;<span class="devsite-syntax-n">!-- /antipatterns/examples/raise-fault-conditions-4.xml  --</span>&gt;
&lt;<span class="devsite-syntax-n">PreFlow name="PreFlow"</span>&gt;
<span class="devsite-syntax-n">    &lt;Request&gt;</span>
<span class="devsite-syntax-n">        …</span>
<span class="devsite-syntax-n">        &lt;Step&gt;</span>
<span class="devsite-syntax-n">            &lt;Name&gt;HandleOptionsRequest&lt;/Name&gt;</span>
<span class="devsite-syntax-n">            &lt;Condition&gt;(request.verb Equals "OPTIONS")&lt;/Condition&gt;</span>
<span class="devsite-syntax-n">        &lt;/Step&gt;</span>
<span class="devsite-syntax-n">        …</span>
&lt;<span class="devsite-syntax-n">/PreFlow</span>&gt;</pre></devsite-code>

<p>
The intent is to return the response to the API client immediately without processing other policies.
  However, this will lead to misleading analytics data because the fault variables will contain the
  RaiseFault policy's name, making the proxy more difficult to debug. The correct way to implement
  the desired behavior is to use Flows with special conditions, as described in
  <a href="/apigee/docs/api-platform/develop/adding-cors-support-api-proxy">Adding CORS support</a>.
</p>

<h2 id="impact" data-text="Impact" tabindex="-1">Impact</h2>

<p>
Use of the RaiseFault policy as described above results in overwriting key fault variables with the
  RaiseFault policy's name instead of the failing policy's name.  In Analytics and NGINX Access logs,
  the<code translate="no" dir="ltr"> x_apigee_fault_code</code> and <code translate="no" dir="ltr">x_apigee_fault_policy<strong> </strong></code>variables
  are overwritten.    In <a href="https://apigee.com/apimonitoring">API Monitoring</a>, the <code translate="no" dir="ltr">Fault Code</code>
  and <code translate="no" dir="ltr">Fault Policy </code>are overwritten. This behavior makes it difficult to troubleshoot and
  determine which policy is the true cause of the failure.

<p>
In the screenshot  below from <a href="https://apigee.com/apimonitoring">API Monitoring</a>,
  you can see that the Fault Code and Fault policy were overwritten to generic <code translate="no" dir="ltr">RaiseFault</code>
  values, making it impossible to determine the root cause of the failure from the logs:
</p>

<img src="/static/apigee/docs/api-platform/images/antipatterns/raise-fault-conditions.png" width="80%" alt="TBD">

<h2 id="best-practice" data-text="Best Practice" tabindex="-1">Best Practice</h2>

<p>
When an Apigee policy raises a fault and you want to customize the error response message,
  use the AssignMessage or JavaScript policies instead of the RaiseFault policy.
</p>
<p>
The RaiseFault policy should be used in a non-error flow. That is, only use RaiseFault to treat a specific
  condition as an error, even if an actual error has not occurred in a policy or in the backend server
  of the API Proxy. For example, you could use the RaiseFault policy to signal that mandatory input
  parameters are missing or have incorrect syntax.
</p>
<p>
You can also use RaiseFault in a fault rule if you want to detect an error during the processing of a
  fault. For example, your fault handler itself could cause an error that you want to signal by using RaiseFault.
</p>
