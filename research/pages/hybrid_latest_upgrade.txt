This procedure covers upgrading from Apigee hybrid version 1.16.x to Apigee hybrid version 1.17.1 and from previous releases of hybrid 1.17.x to version 1.17.1.

Use the same procedures for minor version upgrades (for example version 1.16 to 1.17) and for patch release upgrades (for example 1.17.0 to 1.17.1).

If you are upgrading from Apigee hybrid version 1.15 or older, you must first upgrade to hybrid version 1.16 before upgrading to version 1.17.1. See the instructions for [Upgrading Apigee hybrid to version 1.16](/apigee/docs/hybrid/v1.16/upgrade).

## Changes from Apigee hybrid v1.16

Please note the following changes:

- **Model Context Protocol (MCP) support**: Apigee hybrid version 1.17 adds support for the <a href="https://modelcontextprotocol.io" class="external">Model Context Protocol (MCP)</a>, an open protocol that lets agentic AI applications use your APIs as tools through managed MCP endpoints. Apigee hybrid routes, authorizes, and secures these MCP tool calls the same way it manages your other APIs, so you don't need to run or maintain your own MCP servers. For more information, see [Model Context Protocol (MCP) in Apigee overview](/apigee/docs/api-platform/apigee-mcp/apigee-mcp-overview) and the [MCP quickstart](/apigee/docs/api-platform/apigee-mcp/apigee-mcp-quickstart).
- **Root CA certificate rotation**: Apigee hybrid version 1.17 adds support for rotating the root certificate authority (CA) certificate that anchors trust for TLS communication between your runtime components. You can now replace the root CA before it expires, without downtime, by following a phased rotation procedure. For more information, see [Rotate the root CA certificate](/apigee/docs/hybrid/v1.17/rotate-root-ca).
- **TLS 1.3 support**: Apigee hybrid version 1.17 adds support for TLS 1.3, the latest version of the Transport Layer Security protocol. TLS 1.3 offers faster connection handshakes and stronger security than earlier TLS versions. For information about configuring TLS on the ingress gateway, see [Configuring TLS and mTLS on the ingress gateway](/apigee/docs/hybrid/v1.17/ingress-tls).
- **Forward proxy support for AI policies**: Apigee hybrid version 1.17 adds forward proxy support for the AI policies, such as the Model Armor and semantic caching policies. Outbound calls that these policies make can now be routed through an HTTP forward proxy, which was not supported in earlier versions of Apigee hybrid. For more information, see [Configure forward proxying for API proxies](/apigee/docs/hybrid/v1.17/forward-proxy).
- **Semantic cache Private Service Connect (PSC) endpoint support**: Apigee hybrid version 1.17 adds Private Service Connect (PSC) endpoint support for semantic caching. The semantic caching policies can now reach their backing services over a Private Service Connect endpoint, which keeps that traffic on your private network. For more information, see [Get started with semantic caching policies](/apigee/docs/api-platform/tutorials/using-semantic-caching-policies).

For additional information about features in Hybrid version 1.17, see the [Apigee hybrid v1.17.1 release notes](/apigee/docs/hybrid/release-notes#hybrid_v1171).

## Prerequisites

Before upgrading to hybrid version 1.17, make sure your installation meets the following requirements:

- If your hybrid installation is running a version older than v1.16, you must upgrade to version 1.16 before upgrading to v1.17. See [Upgrading Apigee hybrid to version 1.16](/apigee/docs/hybrid/v1.16/upgrade).
- Helm version v3.14.2+.
- `kubectl`: A supported version of `kubectl` appropriate for your Kubernetes platform version. See [Supported platforms and versions: `kubectl`](/apigee/docs/hybrid/supported-platforms#kubectl).
- cert-manager: A supported version of cert-manager. See [Supported platforms and versions: cert-manager](/apigee/docs/hybrid/supported-platforms#cert-manager). If needed, you will upgrade cert-manager in the [Prepare to upgrade to version 1.17](#prepare) section below.

## Before you upgrade to 1.17.1 - limitations and important notes

- Upgrading to Apigee hybrid version 1.17 may require downtime.

  When upgrading the Apigee controller to version 1.17.1, all Apigee deployments undergo a rolling restart. To minimize downtime in production hybrid environments during a rolling restart, make sure you are running at least two clusters (in the same or different region/data center). Divert all production traffic to a single cluster and take the cluster you are about to upgrade offline, and then proceed with the upgrade process. Repeat the process for each cluster.

  Apigee recommends that once you begin the upgrade, you should upgrade all clusters as soon as possible to reduce the chances of production impact. There is no time limit on when all remaining clusters must be upgraded after the first one is upgraded. However, until all remaining clusters are upgraded Cassandra backup and restore cannot work with mixed versions. For example, a backup from Hybrid 1.16 cannot be used to restore a Hybrid 1.17 instance.

- Management plane changes do not need to be fully suspended during an upgrade. Any required temporary suspensions to management plane changes are noted in the upgrade instructions below.

## Prepare to upgrade to version 1.17

### Back up your hybrid installation

1.  These instructions use the environment variable `APIGEE_HELM_CHARTS_HOME` for the directory in your file system where you have installed the Helm charts. If needed, change directory into this directory and define the variable with the following command:
    <div class="section">

    ### Linux

    <div>

    </div>

    ``` devsite-terminal
    export APIGEE_HELM_CHARTS_HOME=$PWD
    echo $APIGEE_HELM_CHARTS_HOME
    ```

    </div>

    <div class="section">

    ### Mac OS

    <div>

    </div>

    ``` devsite-terminal
    export APIGEE_HELM_CHARTS_HOME=$PWD
    echo $APIGEE_HELM_CHARTS_HOME
    ```

    </div>

    <div class="section">

    ### Windows

    <div>

    </div>

    ``` devsite-terminal
    set APIGEE_HELM_CHARTS_HOME=%CD%
    echo %APIGEE_HELM_CHARTS_HOME%
    ```

    </div>

2.  Make a backup copy of your version 1.16 `$APIGEE_HELM_CHARTS_HOME/` directory. You can use any backup process. For example, you can create a `tar` file of your entire directory with:

    <div>

    </div>

    ``` devsite-click-to-copy
    tar -czvf $APIGEE_HELM_CHARTS_HOME/../apigee-helm-charts-v1.16-backup.tar.gz $APIGEE_HELM_CHARTS_HOME
    ```

3.  Back up your Cassandra database following the instructions in [Cassandra backup and recovery](/apigee/docs/hybrid/v1.17/cassandra-backup-overview).

4.  Make sure that your TLS certificate and key files (`.crt`, `.key`, and/or `.pem`) reside in the `$APIGEE_HELM_CHARTS_HOME/apigee-virtualhost/` directory.

### Upgrade your Kubernetes version

Check your Kubernetes platform version and if needed, upgrade your Kubernetes platform to a version that is supported by both hybrid 1.16 and hybrid 1.17. Follow your platform's documentation if you need help.

### Upgrade cert-manager

**Note:** This procedure is optional if you are using cert-manager 1.16.3 or higher.

Apigee hybrid v1.17 supports cert-manager releases 1.16 through 1.19. There is a change in cert-manager 1.18 that can cause an issue with your traffic. In cert-manager release 1.18, the default value of `Certificate.Spec.PrivateKey.rotationPolicy` was changed from `Never` to `Always`. For upgraded Apigee hybrid installations, this can cause an issue with your traffic. When upgrading to hybrid v1.17 from an earlier version, you must either edit your `apigee-ca` certificate to compensate for this change or keep your version of cert-manager at release 1.17.x or lower.

**Note:** This change affects upgrades from earlier versions of Apigee hybrid only and does not affect fresh installations of Apigee hybrid v1.17.

Before upgrading cert-manager to 1.18 or 1.19, use the following steps procedure to edit your `apigee-ca` certificate to set the value of `Certificate.Spec.PrivateKey.rotationPolicy` to `Never`.

**Warning:** Performe these steps *before* upgrading cert-manager. Otherwise, you may trigger a certificate rotation.

**Note:** For multi-region deployments, the following change to the `apigee-ca` certificate only needs to be made in the primary region. If there is no `apigee-ca` certificate, skip this procedure for clusters in secondary regions.

1.  Check the contents of your `apigee-ca` certificate to see if `rotationPolicy` is set:

    **Tip:** If you are using a custom cert-manager namesspace, replace `cert-manager` with the correct namespace in the following commands.

    <div>

    </div>

    ``` devsite-terminal

    kubectl get certificate apigee-ca -n cert-manager -o yaml
    ```

    Look for the values under `spec.privateKey` in the output:

    <div>

    </div>

    ``` devsite-disable-click-to-copy

    ...
    spec:
      commonName: apigee-hybrid
      duration: 87600h
      isCA: true
      issuerRef:
        group: cert-manager.io
        kind: ClusterIssuer
        name: apigee-root-certificate-issuer
      privateKey:
        algorithm: ECDSA
        # Note: rotationPolicy would appear here if it is set.
        size: 256
      secretName: apigee-ca
    ...
    ```

2.  If `rotationPolicy` is not set or if it is set to `Always`, edit the `apigee-ca` certificate to set the value of `rotationPolicy` to `Never`:
    1.  Perform a dry run first:

        <div>

        </div>

        ``` devsite-terminal

        kubectl patch Certificate \
          --dry-run=server \
          -n cert-manager \
          --type=json \
          -p='[{"op": "replace", "path": "/spec/privateKey/rotationPolicy", "value": "Never"}]' \
          -o=yaml \
          apigee-ca
        ```

    2.  Patch the certificate:

        <div>

        </div>

        ``` devsite-terminal

        kubectl patch Certificate \
          -n cert-manager \
          --type=json \
          -p='[{"op": "replace", "path": "/spec/privateKey/rotationPolicy", "value": "Never"}]' \
          -o=yaml \
          apigee-ca
        ```

3.  Verify that the value of `rotationPolicy` is now set to `Never`:

    <div>

    </div>

    ``` devsite-terminal

    kubectl get certificate apigee-ca -n cert-manager -o yaml
    ```

    The output should look similar to the following:

    <div>

    </div>

    ``` devsite-disable-click-to-copy

    ...
    spec:
      commonName: apigee-hybrid
      duration: 87600h
      isCA: true
      issuerRef:
        group: cert-manager.io
        kind: ClusterIssuer
        name: apigee-root-certificate-issuer
      privateKey:
        algorithm: ECDSA
        rotationPolicy: Never
        size: 256
      secretName: apigee-ca
    ...
    ```

4.  Upgrade cert-manager. The following command will download and install cert-manager v1.19.2:

    <div>

    </div>

    ``` devsite-terminal

    kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.19.2/cert-manager.yaml
    ```

    See [Supported platforms and versions: cert-manager](/apigee/docs/hybrid/supported-platforms#cert-manager) for a list of supported versions.

See:

- [Known issue 465834046](/apigee/docs/release/known-issues#465834046)
- <a href="https://cert-manager.io/docs/releases/release-notes/release-notes-1.18/#the-default-value-of-certificatespecprivatekeyrotationPolicy-is-now-always" class="external">cert-manager Release 1.18: The default value of <code translate="no" dir="ltr">Certificate.Spec.PrivateKey.rotationPolicy</code> is now <code translate="no" dir="ltr">Always</code></a>

## Rolling back to a previous version

To roll back to the previous version, use the older chart version to roll back the upgrade process in the reverse order. Start with `apigee-virtualhost` and work your way back to `apigee-operator`, and then revert the CRDs.

**Tip:** If you know the last release version, you can use the `helm rollback` command rather than the `helm upgrade` command described below.

1.  Revert the charts. The following commands assume you are using the charts from the previous version (v1.16.x).
    1.  Run the following command for each environment group:

        <div>

        </div>

        ``` devsite-terminal

        helm upgrade ENV_GROUP_RELEASE_NAME apigee-virtualhost/ \
          --install \
          --namespace APIGEE_NAMESPACE \
          --atomic \
          --set envgroup=ENV_GROUP_NAME \
          -f 1.16_OVERRIDES_FILE
        ```

    2.  Run the following command for each environment:

        <div>

        </div>

        ``` devsite-terminal

        helm upgrade ENV_RELEASE_NAME apigee-env/ \
          --install \
          --namespace APIGEE_NAMESPACE \
          --atomic \
          --set env=ENV_NAME \
          -f 1.16_OVERRIDES_FILE
        ```

    3.  `apigee-org`:

        <div>

        </div>

        ``` devsite-terminal

        helm upgrade ORG_NAME apigee-org/ \
          --install \
          --namespace APIGEE_NAMESPACE \
          --atomic \
          -f 1.16_OVERRIDES_FILE
        ```

    4.  `apigee-ingress-manager`:

        <div>

        </div>

        ``` devsite-terminal

        helm upgrade ingress-manager apigee-ingress-manager/ \
          --install \
          --namespace APIGEE_NAMESPACE \
          --atomic \
          -f 1.16_OVERRIDES_FILE
        ```

    5.  `apigee-redis`:

        <div>

        </div>

        ``` devsite-terminal

        helm upgrade redis apigee-redis/ \
          --install \
          --namespace APIGEE_NAMESPACE \
          --atomic \
          -f 1.16_OVERRIDES_FILE
        ```

    6.  `apigee-telemetry`:

        <div>

        </div>

        ``` devsite-terminal

        helm upgrade telemetry apigee-telemetry/ \
          --install \
          --namespace APIGEE_NAMESPACE \
          --atomic \
          -f 1.16_OVERRIDES_FILE
        ```

    7.  `apigee-datastore`:

        <div>

        </div>

        ``` devsite-terminal

        helm upgrade datastore apigee-datastore/ \
          --install \
          --namespace APIGEE_NAMESPACE \
          --atomic \
          -f 1.16_OVERRIDES_FILE
        ```

    8.  `apigee-operator`:

        <div>

        </div>

        ``` devsite-terminal

        helm upgrade operator apigee-operator/ \
          --install \
          --namespace APIGEE_NAMESPACE \
          --atomic \
          -f 1.16_OVERRIDES_FILE
        ```

2.  Revert the CRDs by reinstalling the older CRDs.

    <div>

    </div>

    ``` devsite-terminal

    kubectl apply -k apigee-operator/etc/crds/default/ \
      --server-side \
      --force-conflicts \
      --validate=false
    ```
