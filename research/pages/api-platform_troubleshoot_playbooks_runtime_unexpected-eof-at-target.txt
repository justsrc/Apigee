<p style="text-align: right;"><span style="background-color: var(--tenant-background-3); font-size:12pt"><em>This page
applies to <strong>Apigee</strong> and <strong>Apigee hybrid</strong>.</em></p>


<p style="text-align: right;">
  <span style="background-color: var(--tenant-background-3); font-size:12pt"><em>
    View <a href="https://docs.apigee.com/api-platform/get-started/what-apigee-edge" target="_blank">
    Apigee Edge</a> documentation.</em>
  </span>
  <span class="tooltip" title="If you are using Apigee
      Edge for Public or Private Cloud, click this link to view Apigee Edge documentation."
        style="vertical-align:middle;">
      <img src="https://fonts.gstatic.com/s/i/googlematerialicons/help/v13/gm_grey-24dp/1x/gm_help_gm_grey_24dp.png"
           width="2.5%" /> 
  </span>
</p>
 

<p>This playbook can be used to diagnose and resolve 502 Bad Gateway Unexpected EOF errors for both Apigee and Apigee Hybrid.</p>

        <main>
            <section id="symptom" class="mb-8">
                <h2 class="text-2xl font-semibold text-gray-800 border-b pb-2 mb-4" id="symptom" data-text="Symptom" tabindex="-1">Symptom</h2>
                <p class="mt-2">The client application gets an HTTP status code of 502 with the message Bad Gateway as a response for API calls. The HTTP status code 502 means that the client (in this case Apigee) is not receiving a valid response from the backend servers that should actually fulfill the request.</p>
            </section>

            <section id="error-messages" class="mb-8">
                <h2 class="text-2xl font-semibold text-gray-800 border-b pb-2 mb-4" id="error-messages" data-text="Error messages" tabindex="-1">Error messages</h2>
                <p>Client application API calls encountered the following response code:</p>
                <div></div><devsite-code><pre class="devsite-disable-click-to-copy" translate="no" dir="ltr" is-upgraded>HTTP/1.1 502 Bad Gateway</pre></devsite-code>
                <p class="mt-4">In addition, you may observe the following error message:</p>
                <div></div><devsite-code><pre class="devsite-disable-click-to-copy" translate="no" dir="ltr" is-upgraded>{ 
    "fault": { 
        "faultstring": "Unexpected EOF at target", 
        "detail": { 
            "errorcode":"messaging.adaptors.http.flow.UnexpectedEOFAtTarget", 
            "reason":"TARGET_READ_UNEXPECTED_EOF" 
          } 
      } 
}</pre></devsite-code>
            </section>

            <section id="common-diagnosis-steps" class="mb-8">
                <h2 class="text-2xl font-semibold text-gray-800 border-b pb-2 mb-4" id="common-diagnosis-steps" data-text="Common diagnosis steps" tabindex="-1">Common diagnosis steps</h2>
                <p>To diagnose the error, you can use any of the following methods:</p>
                <ul class="custom-list mt-2 space-y-1">
                    <li>API Monitoring</li>
                    <li>Debug session</li>
                    <li>Ingress logs</li>
                    <li>Runtime logs</li>
                </ul>

                <div id="api-monitoring" class="mt-6">
                    <h3 class="text-xl font-semibold text-gray-700" id="api-monitoring" data-text="API Monitoring" tabindex="-1">API Monitoring</h3>
                    <p class="mt-2">Diagnose the error using API Monitoring.</p>
                    <p class="mt-2">In the Google Cloud console, go to the <b>Apigee &gt; Proxy development &gt; API monitoring</b> page.</p>
                    <p><a href="https://console.cloud.google.com/apigee/apimonitoring/investigate"
                      class="button button-primary"
                      target="console"
                      track-name="consoleLink"
                      track-type="tutorial"
                      track-metadata-position="body">Go to API monitoring</a></p>
                    <p class="mt-2">In the <b>API monitoring</b> page, investigate the 502 errors with the following steps:</p>
                    <ol class="custom-list mt-2 space-y-1">
                        <li>On the Apigee UI of the customer project, go to the <strong>Investigate</strong> dashboard.</li>
                        <li>In the drop down menu labeled <strong>Graphs</strong> at the top, make sure that at least <strong>Fault Code by Status Code</strong> and <strong>Fault Source by Proxy</strong> are selected and ensure that the right time period is selected when the 502 errors occurred.</li>
                        <li>Click the box in the matrix when you are seeing a high number of 502 errors.</li>
                        <li>On the right side, you can see the details of the 502 errors which would look something like the following:</li>
                    </ol>
                    <figure class="mt-4">
                        <img src="/static/apigee/docs/api-platform/troubleshoot/playbooks/runtime/images/502_API_Monitoring.png" alt="API Monitoring dashboard showing 502 errors with Fault Code and Fault Source highlighted." class="screenshot">
                        <figcaption class="text-sm text-center text-gray-500 mt-2">API Monitoring view highlighting the Fault Code and Fault Source.</figcaption>
                    </figure>
                    <p class="mt-4">Here you can see the following information:</p>
                    <ul class="custom-list mt-2">
                        <li><strong>Fault Code</strong> is <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">messaging.adaptors.http.flow.UnexpectedEOFAtTarget</code></li>
                        <li><strong>Fault Source</strong> is <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">target</code></li>
                    </ul>
                    <p class="mt-2">This indicates that the 502 error is caused by the target due to unexpected EOF.</p>
                </div>

                <div id="debug-session" class="mt-6">
                    <h3 class="text-xl font-semibold text-gray-700" id="debug-session" data-text="Debug session" tabindex="-1">Debug session</h3>
                    <p class="mt-2">Diagnose the error using a debug session:</p>
                    <ol class="custom-list mt-2 space-y-1">
                        <li>Run a new <a href="https://cloud.google.com/apigee/docs/api-platform/debug/trace" target="_blank" rel="noopener noreferrer" class="anchor-link">debug session</a> while making an API call to reproduce the 502 Bad Gateway error.</li>
                        <li>Select one of the failing requests and examine the trace.</li>
                        <li>Navigate through the various phases of the trace and locate where the failure occurred.</li>
                        <li>You should see the failure after the request has been sent to the target server as shown below (note the screenshot is of debug v1):</li>
                    </ol>
                    <figure class="mt-4">
                        <img src="/static/apigee/docs/api-platform/troubleshoot/playbooks/runtime/images/502_Debug_trace.png" alt="Debug session trace showing Unexpected EOF at target error with properties highlighted." class="w-full rounded-md border">
                        <figcaption class="text-sm text-center text-gray-500 mt-2">Debug session trace highlighting the error details.</figcaption>
                    </figure>
                    <p class="mt-4">Check the property <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">error</code> at the phase the error occurred as can be seen in the above screenshot. The value should contain the message "Unexpected EOF at target".</p>
                    <p class="mt-2">You can also determine the value of <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">X-Apigee.fault-source</code> and <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">X-Apigee.fault-code</code> in the AX (Analytics Data Recorded) Phase in the trace. If the values of <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">X-Apigee.fault-source</code> and <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">X-Apigee.fault-code</code> match the values shown in the following table, you can confirm that the 502 error is coming from the target server:</p>
                    <table class="min-w-full bg-white border mt-4">
                        <thead class="bg-gray-50">
                            <tr>

                <div id="cause-incorrect-target-server">
                    <h3 class="text-2xl font-semibold text-gray-800 border-b pb-2" id="cause:-incorrectly-configured-target-server" data-text="Cause: Incorrectly configured target server" tabindex="-1">Cause: Incorrectly configured target server</h3>
                    <p class="mt-4">The target server is not properly configured to support TLS/SSL connections.</p>

                    <ol class="custom-list mt-2 space-y-2">
                      <li>It is likely that this issue is caused by an incorrect target server configuration if the debug session for the failing API request shows the following:
                          <ul class="custom-list ml-6 mt-2">
                              <li>The 502 Bad Gateway error is seen as soon as the target flow request starts</li>
                              <li>The <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">error.class</code> displays <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">messaging.adaptors.http.flow.UnexpectedEOF</code></li>

                    <div></div><devsite-code><pre class="devsite-disable-click-to-copy" translate="no" dir="ltr" is-upgraded>{

                    <p class="mt-4">The illustrated <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">TargetServer</code> definition is an example of a typical misconfiguration which is explained as follows:</p>
                    <p class="mt-2">Assume that the target server <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">my-apigee-example.sample.appspot.com</code> is configured to accept secure (HTTPS) connections on port 443. However, if you look at the target server definition, there are no other attributes/flags that indicate that it is meant for secure connections. This causes Apigee X to treat the API requests going to the specific target server as HTTP (non-secure) requests. So Apigee X will not initiate the TLS/SSL Handshake process with this target server.</p>
                    <p class="mt-2">Since the target server is configured to accept only HTTPS (TLS/SSL) requests on port 443, it will reject the request from Apigee X or close the connection. As a result, you get an <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">UnexpectedEOFAtTarget</code> error on the apigee-runtime. The apigee-runtime will send 502 Bad Gateway as a response to the client.</p>
                    <h4 class="font-semibold mt-4 text-lg" id="resolution" data-text="Resolution" tabindex="-1">Resolution</h4>
                    <p class="mt-2">Always ensure that the target server is configured correctly as per your requirements. For the illustrated example above, if you want to make requests to a secure (HTTPS TLS/SSL) target server, you need to include the <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">sSLInfo</code> attributes with the <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">enabled</code> flag set to true. While it is allowed to add the <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">sSLInfo</code> attributes for a target server in the target endpoint definition itself, it is recommended to add the SSLInfo attributes as part of the target server definition to avoid any confusion. You can enable all necessary attributes at the target server directly as shown below:</p>
                    <figure class="mt-4">
                        <img src="/static/apigee/docs/api-platform/troubleshoot/playbooks/runtime/images/502_target_server.png" alt="Update Target Server UI with Enable SSL toggled on" class="w-full rounded-md border">

                <div id="cause-keep-alive-timeout">
                    <h3 class="text-2xl font-semibold text-gray-800 border-b pb-2" id="cause:-incorrectly-configured-keep-alive-timeout" data-text="Cause: Incorrectly configured keep alive timeout" tabindex="-1">Cause: Incorrectly configured keep alive timeout</h3>
                    <p class="mt-4">Before you diagnose if this is the cause for the 502 errors, please read through the following concepts.</p>
                    <h4 class="font-semibold mt-4 text-lg" id="persistent-connections-in-apigee" data-text="Persistent connections in Apigee" tabindex="-1">Persistent connections in Apigee</h4>
                    <p class="mt-2">Apigee X by default follows the HTTP/1.1 standard and uses persistent connections when communicating with the target backend server. Persistent connections can increase performance by allowing an already established TCP and (if applicable) TLS/SSL connection to be re-used, which reduces latency overheads. The duration for which a connection needs to be persisted is controlled through the keep alive timeout property (in Apigee's target endpoint config, this property is called <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">keepalive.timeout.millis</code>).</p>
                    <p class="mt-2">Both the backend server and the Apigee apigee-runtime use keep alive timeouts to keep connections open with one another. Once no data is received within the keep alive timeout duration, the backend server or apigee-runtime can close the connection with the other.</p>
                    <p class="mt-2">API Proxies deployed to an apigee-runtime in Apigee X, by default, have a keep alive timeout set to 60 seconds unless overridden. Once no data is received for 60s, Apigee will close the connection with the backend server. The backend server will also maintain a keep alive timeout, and once this expires the backend server will close the connection with the apigee-runtime.</p>
                    <h4 class="font-semibold mt-4 text-lg" id="implication-of-incorrect-keepalive-timeout-configuration" data-text="Implication of incorrect keepalive timeout configuration" tabindex="-1">Implication of incorrect keepalive timeout configuration</h4>
                    <p class="mt-2">If either Apigee or the backend server is configured with incorrect keep alive timeouts, then it results in a race condition which causes the backend server to send an unexpected End Of File (FIN) in response to a request for a resource.</p>
                    <p class="mt-2">For example, if the keep alive timeout is configured within the API Proxy or the apigee-runtime with a value greater than or equal to the timeout of the upstream backend server, then the following race condition can occur. That is, if the apigee-runtime does not receive any data until very close to the threshold of the backend server keep alive timeout, but a request comes through and is sent to the backend server using the existing connection, it can lead to 502 Bad Gateway due to Unexpected EOF error as explained below:</p>
                    <ul class="custom-list mt-2 space-y-1">
                        <li>Assume the keep alive timeout set on both the apigee-runtime and the backend server is 60 seconds and no new request came until 59 seconds after the previous request was served by the specific apigee-runtime.</li>
                        <li>The apigee-runtime goes ahead and processes the request that came in at the 59th second using the existing connection (as the keep alive timeout has not yet elapsed) and sends the request to the backend server.</li>
                        <li>However, before the request arrives at the backend server the keep alive timeout threshold has since been exceeded on the backend server.</li>
                        <li>The apigee-runtime 's request for a resource is in-flight, but the backend server attempts to close the connection by sending a FIN packet to the apigee-runtime.</li>
                        <li>While the apigee-runtime is waiting for the data to be received, it instead receives the unexpected FIN, and the connection is terminated.</li>
                        <li>This results in an Unexpected EOF and subsequently a 502 error is returned to the client by the apigee-runtime.</li>
                    </ul>
                     <p class="mt-2">In this case, we observed the 502 error occurred because the same keep alive timeout value of 60 seconds was configured on both the apigee-runtime and backend server. Similarly, this issue can also happen if a higher value is configured for keep alive timeout on the apigee-runtime than on the backend server.</p>
                    <h4 class="font-semibold mt-4 text-lg" id="diagnosis_2" data-text="Diagnosis" tabindex="-1">Diagnosis</h4>
                    <p class="mt-2">Use API Monitoring, Debug sessions or Ingress logs as demonstrated in the <a href="#common-diagnosis-steps" class="anchor-link">Common diagnosis steps</a> to determine the message ID, fault code, and fault source for the 502 error.</p>
                    <p class="mt-4">The following log is an example of an Istio Gateway log (Hybrid only) created when the backend closes the connection abruptly (the example is shortened a bit).                     <p class="mt-2">The error <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">java.io.EOFException: eof unexpected</code> indicates that the apigee-runtime received an EOF while it was still waiting to read a response from the backend server.</p>
                    <p class="mt-2">The attribute <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">useCount=7</code> in the error message indicates that the apigee-runtime had re-used this connection about seven times and the attribute <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">bytesWritten=1303</code> indicates that the apigee-runtime had sent the request payload of 1303 bytes to the backend server. However it received zero bytes back when the unexpected EOF error occurred.</p>
                    <p class="mt-2">This shows that the apigee-runtime had re-used the same connection multiple times, and on this occasion it sent data but shortly afterwards received an EOF before any data was received. This means there is a high probability that the backend server's keep alive timeout is shorter or equal to that set in the API proxy.</p>
                    <p class="mt-2">You can investigate further with the help of tcpdump as explained below.</p>
                    <ol class="custom-list mt-2 space-y-2">
                      <li>If you don't find any errors or information in your backend server, collect the packet capture on the first hop right after Apigee with the following command:
                    <div></div><devsite-code><pre class="devsite-terminal" translate="no" dir="ltr" is-upgraded>tcpdump -i any -s 0 host &lt;BACKEND_HOSTNAME&gt; -w &lt;FILENAME&gt;</pre></devsite-code></li>
                      <li>(Hybrid only) You might also want to collect the packet capture on the apigee-runtime by following the community article on <a href="https://discuss.google.dev/t/apigee-hybrid-container-traffic-analysis-with-tcpdump-for-target-requests/18242" target="_blank" rel="noopener noreferrer" class="anchor-link">How to take a tcpdump</a>. For GKE only, you could follow <a href="https://cloud.google.com/container-optimized-os/docs/how-to/toolbox" target="_blank" rel="noopener noreferrer" class="anchor-link">https://cloud.google.com/container-optimized-os/docs/how-to/toolbox</a>.</li>
                      <li>Analyze the tcpdump captured:</li>
                      <figure class="mt-4">
                       <img src="/static/apigee/docs/api-platform/troubleshoot/playbooks/runtime/images/502_tcpdump_2.png" alt="TCPDump showing a successful request followed by a FIN, ACK on connection reuse." class="w-full rounded-md border">
                       <figcaption class="text-sm text-center text-gray-500 mt-2">Sample tcpdump showing a keep-alive timeout issue.</figcaption>
                     </figure>
                    </ol>
                   <p class="mt-4">In the above sample tcpdump, you can see the following:</p>
                    <ul class="custom-list mt-2 space-y-1">
                        <li>In packet 5992, the backend server received a GET request.</li>
                        <li>In packet 6064, it responds with 200 OK.</li>
                        <li>In packet 6084, the backend server received another GET request.</li>
                        <li>In packet 6154, it responds with 200 OK.</li>
                        <li>In packet 6228, the backend server received a third GET request.</li>
                        <li>This time, the backend server returns a FIN, ACK to the apigee-runtime (packet 6285) initiating the closure of the connection.</li>
                    </ul>
                    <p class="mt-2">The same connection was re-used twice successfully in this example, but on the third request, the backend server initiates a closure of the connection, while the apigee-runtime is waiting for the data from the backend server. This suggests that the backend server's keep alive timeout is most likely shorter or equal to the value set in the API proxy.</p>
                   <h4 class="font-semibold mt-4 text-lg" id="compare-keep-alive-timeout-on-apigee-and-backend-server" data-text="Compare keep alive timeout on Apigee and backend server" tabindex="-1">Compare keep alive timeout on Apigee and backend server</h4>
                   <ol class="custom-list mt-2 space-y-2">
                   <li>By default, Apigee X uses a value of 60 seconds for the keep alive timeout property.</li>
                   <li>However, it is possible that the customer may have overridden the default value in the API Proxy. You can verify this by checking the specific TargetEndpoint definition in the failing API Proxy that is giving 502 errors. This is a sample TargetEndpoint configuration where the keep alive timeout property is overridden with a value of 30 seconds (30000 milliseconds):</li>
                    <div></div><devsite-code><pre class="devsite-disable-click-to-copy" translate="no" dir="ltr" is-upgraded>&lt;TargetEndpoint name="default"&gt; 
 &lt;HTTPTargetConnection&gt; 
    &lt;URL&gt;https://mocktarget.apigee.net/json&lt;/URL&gt; 
    &lt;Properties&gt; 
      &lt;Property name="keepalive.timeout.millis"&gt;30000&lt;/Property&gt; 
    &lt;/Properties&gt; 
  &lt;/HTTPTargetConnection&gt; 
&lt;/TargetEndpoint&gt;</pre></devsite-code>
                    <li>Next, check the keep alive timeout property configured on your backend server. Assume that your backend server is configured with a value of 25 seconds.</li>
                    <li>If you determine that the value of the keep alive timeout property on Apigee is higher than the value of the keep alive timeout property on the backend server as in the above example, then that is the cause for 502 errors.</li>
                    </ol>
                    <h4 class="font-semibold mt-4 text-lg" id="resolution_2" data-text="Resolution" tabindex="-1">Resolution</h4>
                    <p class="mt-2">Ensure that the keep alive timeout property is always lower on Apigee (in the API Proxy and apigee-runtime component) compared to that on the backend server.</p>
                    <ol class="custom-list mt-2 space-y-2">
                       <li>Determine the value set for the keep alive timeout on the backend server.</li>
                       <li>Configure an appropriate value for the keep alive timeout property in the API Proxy or apigee-runtime, such that the keep alive timeout property is lower than the value set on the backend server, using the steps described in <a href="https://cloud.google.com/apigee/docs/api-platform/antipatterns/http-persistent-connections" target="_blank" rel="noopener noreferrer" class="anchor-link">Antipattern: Disable HTTP persistent (reusable keep-alive) connections</a>.</li>
                    </ol>
                </div>

                <div id="cause-nat-aws-nlb">
                    <h3 class="text-2xl font-semibold text-gray-800 border-b pb-2" id="cause:-nat-usage-with-aws-nlb-target-with-cross-zone-load-balancing-and-ip-preservation" data-text="Cause: NAT usage with AWS NLB target with cross-zone load balancing and IP preservation" tabindex="-1">Cause: NAT usage with AWS NLB target with cross-zone load balancing and IP preservation</h3>
                    <p class="mt-4">(Apigee X only) If you are using AWS NLB as a target, you might encounter the following issue:</p>
                    <p class="mt-2">Suppose AWS NLB has 3 IPS:<br><br>
                    203.0.113.1:443 (AZ 1)<br>203.0.113.2:443 (AZ 2)<br> 203.0.113.3:443 (AZ 3)</p>
                    <p class="mt-2">Apigee X establishes following connection:
                      <ul class="custom-list mt-2 space-y-1">
                    <li>192.0.2.10:30009 -> 203.0.113.1:443</li>
                    <li>192.0.2.10:30009 -> 203.0.113.1:443 (existing)</li>
                    <li>192.0.2.10:30009 -> 203.0.113.2:443 (new)</li>
                    </ul>
                    <p class="mt-2">This is a valid behavior.</p>
                    <p class="mt-2">The problem occurs if 203.0.113.1:443 and 203.0.113.2:443 point to the same NLB backend. If so, the backend will receive packets belonging to two different connections but arriving from the same source. Which will break both connections.</p>
                    <p class="mt-2">First connection might fail with the same EOF error, although other errors are possible.</p>
                    <h4 class="font-semibold mt-4 text-lg" id="diagnosis_3" data-text="Diagnosis" tabindex="-1">Diagnosis</h4>
                    <p class="mt-2">Verify if <strong>all</strong> conditions below are true:</p>
                    <ul class="custom-list mt-2 space-y-1">
                        <li><a href="https://cloud.google.com/apigee/docs/api-platform/security/nat-provisioning" target="_blank" rel="noopener noreferrer" class="anchor-link">NAT IPs are provisioned</a></li>
                        <li><a href="https://docs.aws.amazon.com/elasticloadbalancing/latest/network/introduction.html" target="_blank" rel="noopener noreferrer" class="anchor-link">Target is AWS NLB</a></li>
                        <li><a href="https://docs.aws.amazon.com/elasticloadbalancing/latest/network/network-load-balancers.html#cross-zone-load-balancing" target="_blank" rel="noopener noreferrer" class="anchor-link">Cross-zone load balancing is enabled.</a></li>
                        <li><a href="https://docs.aws.amazon.com/elasticloadbalancing/latest/network/load-balancer-target-groups.html#target-group-attributes" target="_blank" rel="noopener noreferrer" class="anchor-link">Client IP preservation is enabled.</a></li>
                    </ul>
                    <p class="mt-2">If so, the issue <strong>should</strong> intermittently occur. Since issues can be diagnosed by the conditions above, .pcap is not necessary. However, it is possible to spot it on the target networking capture, but not the Apigee capture.</p>
                     <h4 class="font-semibold mt-4 text-lg" id="target-.pcap-diagnosis" data-text="Target .pcap diagnosis" tabindex="-1">Target .pcap diagnosis</h4>
                     <p class="mt-2">To spot it on the target capture in Wireshark:</p>
                     <ol class="custom-list mt-2 space-y-1">
                        <li>Filter by the port of the affected connection: e.g. tcp.port == 30009</li>
                        <li>Right click on Column -> Column Preferences. Add Column of Type: Custom. Field: tcp.seq_raw. This will display raw sequence numbers.</li>
                        <li>Look for any new sequence numbers for packets with Apigee source IP. For example, if you see a raw sequence number starting with 384... and suddenly it switches to 376... without a valid use-case for a port reuse, it is a conflicting connection.</li>
                    </ol>
                    <h4 class="font-semibold mt-4 text-lg" id="resolution_3" data-text="Resolution" tabindex="-1">Resolution</h4>
                    <p class="mt-2">Disable <a href="https://docs.aws.amazon.com/elasticloadbalancing/latest/network/network-load-balancers.html#cross-zone-load-balancing" target="_blank" rel="noopener noreferrer" class="anchor-link">Cross-zone load balancing</a> or <a href="https://docs.aws.amazon.com/elasticloadbalancing/latest/network/load-balancer-target-groups.html#target-group-attributes" target="_blank" rel="noopener noreferrer" class="anchor-link">Client IP preservation.</a></p>
                    <p class="mt-2">Cloud NAT behaves correctly here, and this is an issue with NLB architecture. No changes can be made at Apigee.</p>
                </div>
            </section>

            <section id="must-gather" class="mt-8 border-t pt-6">
                <h2 class="text-2xl font-semibold text-gray-800 border-b pb-2 mb-4" id="must-gather-diagnostic-information" data-text="Must gather diagnostic information" tabindex="-1">Must gather diagnostic information</h2>
                <p>If the problem persists even after following the above instructions, gather the following diagnostic information, and then contact <a href="https://cloud.google.com/support-hub" target="_blank" rel="noopener noreferrer" class="anchor-link">Google Cloud Customer Care</a></p>
                <ul class="custom-list mt-2 space-y-1">
                    <li>Google Cloud project ID</li>
                    <li>Apigee organization</li>
                    <li>API proxy and revision</li>
                    <li>A downloaded debug session file for a failing API call.</li>
                    <li>Backend server logs corresponding to the time of the failures.</li>
                    <li>A <code class="bg-gray-200 px-1 rounded" translate="no" dir="ltr">tcpdump</code> packet capture from the Message Processor or the backend server during the failure.</li>
                </ul>
            </section>
